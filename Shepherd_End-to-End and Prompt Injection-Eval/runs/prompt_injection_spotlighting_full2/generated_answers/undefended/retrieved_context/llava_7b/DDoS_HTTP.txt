How should rate limiting and throttling be applied during DDoS HTTP mitigation?

Reference Answer:
The administrator should apply per-source, per-subnet, per-token, per-device, and per-route rate limits where supported. Lower thresholds should be used for login, token refresh, password reset, search, configuration, and firmware download routes. Adaptive throttling should be applied when error rates, backend latency, or queue depth exceed normal thresholds. Abusive clients should receive lightweight error responses rather than being allowed to reach expensive application logic.

Generated Answer:
To apply rate limiting and throttling during DDoS HTTP mitigation, the following steps can be taken based on the retrieved mitigation-guide chunks:

1. Apply per-source, per-subnet, per-token, per-device, and per-route rate limits where supported.
2. Use lower thresholds for login, token refresh, password reset, search, configuration, and firmware download routes.
3. Apply adaptive throttling when error rates, backend latency, or queue depth exceed normal thresholds.
4. Return lightweight error responses for abusive clients rather than allowing requests to reach expensive application logic.
5. Cache static assets, documentation pages, firmware metadata, status pages, and repeated read-only responses.
6. Serve static or degraded-mode pages for dashboards when backend systems are overloaded.
7. Disable or defer nonessential expensive operations such as broad search, heavy reports, bulk export, or historical queries.
8. Use connection reuse and upstream keep-alive settings to reduce backend connection churn.
9. Apply web application firewall controls such as blocking malformed HTTP methods, invalid headers, suspicious payloads, and request patterns that do not match the service design.
10. Use allowlists for sensitive management routes when those routes should only be reachable from known administrative networks.
11. Apply bot-management or challenge mechanisms only when they do not interfere with legitimate device clients.
12. Configure connection limits, request body limits, header size limits, idle timeouts, and backend timeout policies.
13. Use queue limits and circuit breakers to prevent a flooded route from exhausting the entire application.
14. Protect backend databases, message brokers, and authentication services with their own limits and monitoring.

By applying these rate limiting and throttling measures, you can effectively mitigate DDoS HTTP attacks and ensure that legitimate administrators and devices have access to essential services while preventing abuse and reducing the impact of future events.

Based on the given incident summary and retrieved mitigation-guide chunks, the following investigation workflow should be followed after DDoS HTTP activity is detected:

1. Immediate Stabilization: Identify the protected service, affected route, application endpoint, or management portal under load. Confirm whether the traffic is public-facing, internal, device-originated, or passing through a gateway or proxy. Enable emergency rate limits at the closest effective control point, such as the load balancer, reverse proxy, API gateway, web application firewall, or edge firewall. Monitor authentication attempts and management activity after credentials are rotated. Validate that the device performs its operational function without unexpected peer communication. Keep enhanced logging enabled for a defined observation period after restoration.

5. Administrator Checklist: Answer the following operational questions before the incident is closed: Which endpoint was affected, and what operational role does it serve? What network paths allowed the attacker to control or communicate with the device? Which accounts, keys, tokens, or certificates may have been exposed? What persistence mechanism was identified and removed? Were peer devices checked for lateral movement or shared compromise conditions? By following this workflow, the IoT Shepherd can ensure a thorough investigation and mitigation process after DDoS HTTP activity is detected.
